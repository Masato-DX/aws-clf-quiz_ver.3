新規リポジトリで Claude Code セッションを開始し、以下をそのまま貼り付ける。
`★ここを埋める` の表だけ、対象試験に合わせて書き換えること。

## 1. 今回作る試験（★ここを埋める）

| 項目 | 値 |
|---|---|

## 2. 進め方

一度に全部作らず、以下のフェーズで進めてください。各フェーズの終わりに報告を挟むこと。

### Phase 1: 設計の確認
- ドキュメントを読み、上記の試験情報を踏まえた実装計画を提示する
- 領域・難易度・モジュールの分類定義（taxonomy）を確定する
- 既存アプリからの変更点と、そのまま流用する箇所を明示する
- ここで一度止めて、こちらの確認を待つこと

### Phase 2: 骨格の実装
- design.md「13.1 ファイル分割案」の構成で実装する
  （domain/ と analytics.js を React から切り離し、テスト可能にすること）
- 問題データはシード 20 問程度で先に動く状態にする
- design.md「13.2 優先的に書くべきテスト」のテストを実装し、通ることを確認する
- npm run build が通り、実際に画面が動くことを確認してから報告する

### Phase 3: 問題データの作成
- 目標問題数まで、50問ずつのバッチで作成する
- 各バッチの後に、requirements.md「7.1 文字数バランスの判定基準」で自己検証し、
  基準を満たさない問題は作り直してから次のバッチへ進む
- 領域 × 難易度の配分が偏らないようにする

### Phase 4: 仕上げとデプロイ
- アイコン・マニフェスト・メタタグを対象試験向けに作成する
- design.md「15. 既知の制約」の I-2 / I-3 / I-6 / I-8 を解消した実装になっているか確認する
- CLAUDE.md と docs/（要件定義書・詳細設計書）を新アプリ向けに書き起こす
- デプロイまで実施する

## 3. 必ず守ること

- 学習アルゴリズム（出題選択の優先度・苦手問題の追跡・昇華処理）は
  requirements.md「4. 学習アルゴリズム要件」の仕様を変えずに移植すること。
  これが実運用で 3 回改善した本アプリの中核価値です。
- 問題の選択肢は文字数を揃えること。正解だけが長い／短い状態を作らないこと。
  知識がなくても文の長さで正解が分かってしまう問題は不合格です。
- PAT・Gist ID などの機密情報をコードやコミットに含めないこと。
- push 前に必ず npm run build が通ることを確認すること。
- コミットメッセージは日本語で簡潔に書くこと。
- 問題データは、公開されている試験ガイドの出題範囲に基づいて作成すること。
  実際の試験問題の複製は行わないこと。

## 補足

### リポジトリの準備

新規リポジトリは事前に GitHub 上で作成し、そのリポジトリで Claude Code セッションを開始するのが確実。
セッションの GitHub 連携は開始時のリポジトリにスコープされるため、セッション内から別リポジトリを
作成させるより手戻りが少ない。

### 参照ドキュメントの URL について

`Masato-DX/aws-clf-quiz_ver.3` が **public** であることが前提。
private に変更した場合は raw URL の取得に失敗するため、その際はドキュメントを
新リポジトリへコピーするか、貼り付けで渡すこと。

### モジュール軸が不要な場合

学習モジュール（公式教材の章立て）による絞り込みは AWS Skill Builder 向けの機能。
対象試験に対応する公式教材がない場合は「不要」と書けば、領域のみの単軸になり実装が簡素になる。
